## 弱斷言修正（commit `2945ecf`）

### 1. `test_virtual_keys.py` `test_app_alias_unique` — 只檢查數量為 1

**問題**：只斷言 `/key/list` 回傳 1 筆，沒有確認那一筆就是預期的 key。
**修正**：改用 `return_full_object=true` 取完整物件，斷言
- alias 清單**恰好等於** `[alias]`；
- 該筆的 `token` 等於 `.env` 中 key 的 SHA-256，證明唯一的那把就是應用正在使用的 key。

### 2. `test_virtual_keys.py` `test_parallel_limit` — 只要求「至少一個 200 與一個 429」

**問題**：同時送 4 個請求，接受任何含 200 與 429 的組合；其他錯誤碼（如 500）也會通過。
結果也取決於執行緒時序（第一個請求太快結束時，200 的數量會變多）。

**修正（以固定做法消除時序，不放寬斷言）**：
- 用 `max_parallel_requests=N`（N=2）的臨時 key，依序開 N 個**長串流請求**，每個都讀到第一個內容 chunk 才算「確實在處理中」，因此必定佔住 N 個名額；
- 在串流仍開著時送第 N+1 個請求；
- 斷言：回應碼只能是 200 或 429，且**精確等於** `[200]*N + [429]`；
- 串流讀完後固定等 1 秒（slot 釋放為非同步），再送一次請求，斷言為 200，證明限制的是「並發」而非「次數」。

**不穩定來源說明**：舊做法的不確定性來自執行緒排程（請求是否真的重疊）。新做法的請求重疊由串流保證，與排程無關。
rpm 測試使用全新的臨時 key，計數窗口從該 key 的第一個請求開始，不會跨越時間窗邊界，維持精確斷言 `[200, 200, 429]`。

**同類收緊**：`test_tpm_limit` 改為回應碼只能是 200 或 429，至少一個 200 後恰好一個 429 結束。

**故意設錯檢查**：把臨時 key 的上限暫時改為 N+1（仍只佔 N 個名額）→ 測試失敗：
`assert [200, 200, 200] == [200, 200, 429]`；以 `git checkout` 還原後重跑通過。

### 3. `test_virtual_keys.py` `test_bootstrap_replaces_orphan_alias` — orphan 建立未檢查

**問題**：建立 orphan key 的請求未檢查狀態；若建立失敗，`bootstrap` 會走一般新建路徑，測試仍通過，orphan 處理邏輯其實沒被驗到。
**修正**：
- 前置條件：斷言 orphan 建立回 200 且有 key，並以 `/key/info` 確認存在；
- 事後斷言：orphan key 的 `/key/info` 不再是 200（已被刪除，而非僅被遮蔽）、新 key 與 orphan 不同、該 alias 下唯一的 token 等於新 key 的雜湊。

### 4. `test_containers.py` `test_internal_services_reachable_in_network` — 只檢查 HTTP status

**問題**：Ollama `/api/version` 只檢查 200，沒有驗證回應內容。
**修正**：從 `docker compose config --images` 取出 `ollama/ollama` 的釘選 tag，斷言回應**精確等於** `{"version": "<pinned tag>"}`（目前 `0.40.18`）；Qdrant `/readyz` 的回應內容也一併斷言為 `all shards are ready`。
