## Reading the numbers

- **Saturation at c = 4 = `OLLAMA_NUM_PARALLEL`.** Total throughput grows almost linearly
  up to 4 concurrent streams (85 → 161 → 289 tok/s) and is flat after (280–288 tok/s).
- **Beyond 4, extra concurrency only adds queueing.** TTFT jumps from 0.12 s (c=4) to 3.7 s (c=8)
  and 10.7 s (c=16): requests wait for whole generations (~3.5 s each at 256 tokens) to free a slot.
  Latency grows the same way; per-request decode speed stays at 71–86 tok/s.
- **Per-user experience is good up to 4 concurrent users:** TTFT p95 ≤ 0.13 s, ~75–86 tok/s.
- **Gateway limits match capacity:** the app keys' `max_parallel_requests` (2 + 2) sum to the 4
  slots, so under real app traffic the gateway answers excess requests with 429 immediately
  instead of letting them queue for seconds inside Ollama.

## Operational risk: 2-stream throughput halves after an overload (Ollama 0.40.18)

**What:** after Ollama has served more concurrent streams than it has slots
(`OLLAMA_NUM_PARALLEL=4`), two concurrent streams no longer run at full speed: each drops from
~84 to ~39 tok/s, so 2-stream throughput falls from ~165 to 77–89 tok/s (**−46 % to −53 %**).
It **does not recover on its own**. Only an Ollama restart brings it back. Single streams and
4 streams are not affected.

**Why it matters in production:** an overload is not exotic. In this platform's gateway, the
app keys' parallel limits sum to exactly the 4 slots. But any other client or an unlimited key
(admin, load test), a limiter drift (see `docs/upstream/litellm-parallel-counter.md`) or a
future raise of the limits can push Ollama past 4. After that, the most common real load, two
users at once, gets about half the speed until someone restarts the backend. Nothing on the
dashboard flags it: requests still succeed, they are only slower.

Reading the per-request data (`requests.csv`):

- **Degraded requests come in pairs.** Both concurrent streams take ~6.6 s instead of ~3.1 s for
  256 tokens (~39 tok/s each). TTFT stays normal (≤ 0.07 s), so the slowdown is in decoding.
  This pattern would fit the two sequences no longer being batched together, but that is a guess.
- **The onset can be partial.** In cycle 2, right after the overload only 2 of 8 requests (one
  pair) were degraded (128.8 tok/s); in the next c=2 run 6 of 8 were (89.3 tok/s). In cycle 1
  all 8 requests of both c=2 runs were degraded immediately.
- c=1 (89 tok/s) and c=4 (284–296 tok/s) match the fresh baseline. At c=4 the problem is not
  visible.
- **Root cause not investigated.** What the data shows: the same requests through the same,
  un-restarted LiteLLM recover fully after restarting only Ollama. So the state that causes the
  slowdown lives in the Ollama process, not in the gateway. Where exactly inside Ollama (its
  scheduler, llama.cpp, the GPU driver) is unknown.

**Mitigations (not implemented, for decision):**

1. Keep the gateway's parallel limits summed at ≤ `OLLAMA_NUM_PARALLEL`, and make sure no other
   client bypasses the gateway (already enforced: Ollama has no host port).
2. Detect it. Alert when the per-request decode speed for 2 concurrent requests drops below
   ~60 tok/s. LiteLLM exposes output tokens and latency per request, which is enough for a rough
   tokens/s per request panel.
3. Restart Ollama on a schedule or after detected overload (≈ 10–20 s of unavailability,
   model reload included).
4. Re-test on a newer Ollama, or on vLLM (planned), whose continuous batching should not have
   this failure mode. This needs to be verified with the same script.

## Methodology notes (why `--restart-backend`)

The first sweep ran all levels back-to-back on one Ollama process and was **not** comparable:

| | c=1 | c=2 | c=4 | c=8 | c=16 |
|---|---:|---:|---:|---:|---:|
| Throughput tok/s, back-to-back sweep | 84.1 | 156.0 | 204.5 | 271.8 | 276.0 |
| TTFT p95, back-to-back sweep | 0.080 s | 0.104 s | **5.324 s** | 3.823 s | 11.457 s |

Two state-dependent effects were isolated:

1. **One-off stall at the start of a level.** In that sweep, the first 4 requests of c=4 all waited
   5.3 s together; the remaining 12 had TTFT ≈ 0.1 s. Re-running c=4 alone twice gave TTFT p95 0.12 s
   and 282 tok/s, i.e. not reproducible.
2. **c=2 degrades after oversubscription (reproducible).** On a freshly restarted Ollama, c=2
   gives ~165 tok/s; after a c=8 level it drops to 77–89 tok/s until Ollama restarts. See
   **Operational risk** above for the measurements.

`--restart-backend` restarts Ollama and warms up before every level, so each level starts from the
same state. Treat Ollama numbers as "fresh process"; under long mixed real-world traffic,
2-stream throughput can be lower. Worth re-checking after switching to vLLM.

## Caveats

- Shared desktop machine (browser, Discord, Parsec and other GPU clients running), not a dedicated server.
- One repetition per level and small samples (8–64 requests): treat as indicative, not definitive.
- Output length fixed by `max_tokens=256` (all answers hit the cap); short answers would show
  higher request rates and lower latency.
- Context length is Ollama's default 4096; long RAG prompts (phase 2) will raise TTFT (prefill).
